3.3 System Architecture

Purpose:
Provide a high-level technical overview of how the major components of the implemented system connect and how data moves through them. This section should act as the bridge between the datasets described in Section 3.2 and the detailed component descriptions beginning in Section 3.4. It should answer "What does the complete system look like?" rather than explaining how each component works.

This section should be relatively short, probably around 250-400 words plus an architecture diagram. Much of the conceptual rationale for the architecture has already been established in the Literature Review, while Section 3.1 has already described the experimental design. Avoid repeating either.

Paragraph 1 - Overall architecture:

State that the implemented system consists of several sequential components connecting the prepared input corpora to structured biomedical extractions and ultimately the knowledge graph.
Introduce the overall data flow at a high level.
A suitable representation of the final system may be approximately:

Prepared abstract -> LLM-based joint NER + RE -> structured extraction -> entity normalisation -> ontology-based validation -> knowledge graph construction -> evaluation

Be precise about the actual ordering used by the final implementation.
If ontology validation occurs after NEN and before graph insertion, show that explicitly.
If some validation occurs during NEN itself, reflect the actual implementation rather than forcing these into artificial separate stages.
Do not explain what NER, RE, NEN, or a KG are. These have already been established extensively in Chapter 2.

Paragraph 2 - Input and extraction flow:

Briefly explain that the standardised representations produced in Section 3.2.3 provide the input to the extraction system.
State that title/abstract text is passed to the LLM extraction component.
State that NER and RE are performed jointly by the LLM rather than as separate sequential models, if this accurately reflects the implementation.
State that the model returns structured entity and relation predictions.
State that these outputs are parsed into the internal/tabular representation required by later stages.
Do not describe the model, API parameters, prompt wording, JSON schema, or parsing logic. These belong in Section 3.4.

Paragraph 3 - Normalisation and graph flow:

State that extracted entity mentions subsequently undergo entity normalisation to map them to canonical identifiers.
State what ontology/terminology resources are involved at a high level, but leave the actual mapping procedure for Section 3.4.4.
Briefly state that ontology-based validation is used before/during graph construction, if this reflects the final implementation.
State that validated entities and relations are then converted into graph nodes and edges.
Do not re-explain why normalisation prevents duplicate nodes or why ontologies improve KG consistency. That conceptual rationale has already been established in Section 2.3.

Paragraph 4 - Architecture across experimental stages:

Briefly clarify that the same underlying extraction architecture is used across BioRED and the CBC.
The input dataset and availability of ground-truth annotations differ, but the extraction components themselves remain consistent.
If relevant, state that pipeline configurations changed during EPI development, but that the overall architecture remained stable.
Make clear that after final EPI selection the configuration was frozen before final benchmark and contemporary evaluation.
Keep this extremely brief because Section 3.1 already explains the development/evaluation separation and Section 3.5 will explain EPI development.

This would make the architecture figure more informative than simply showing a straight pipeline.

Important distinctions:

"What experiment was conducted, and how were development and evaluation organised?"

Section 3.2 Datasets should answer:
"What data was used and how was it prepared?"

Section 3.3 System Architecture should answer:
"What are the major implemented components, and how does data flow between them?"

Section 3.4 Information Extraction Pipeline should answer:
"Exactly how does the extraction and normalisation system operate?"

Section 3.5 Pipeline Development should answer:
"How was that system iteratively modified and how was the final EPI selected?"

Section 3.6 Contemporary Knowledge Graph Construction should answer:
"How were the frozen system's contemporary extractions transformed into the final KG?"

Section 3.7 Evaluation should answer:
"How was performance measured at extraction, generalisation, and graph levels?"

Specific repetition concern based on the current Methodology:

Section 3.1 already states that the study consists of extraction development, EPI selection, evaluation, and KG construction. Do not list these four experimental stages again in 3.3.
Section 3.2.3 already explains that BioRED and CBC data become standardised pipeline-ready CSV files. In 3.3, simply begin from "prepared input data" or refer back to Section 3.2.3.
Section 3.1 already explains that the final EPI is frozen before contemporary evaluation. Mention this only if necessary to interpret the architecture.
The purpose of 3.3 should therefore be primarily technical/visual rather than another narrative overview of the project.

Overall recommendation:
Keep 3.3 lean. A strong architecture diagram plus approximately three concise paragraphs would probably be better than a full page of prose. The reader has already been told what the study does; this section should now let them visually understand how the actual software components fit together before Section 3.4 starts opening those components up individually.
