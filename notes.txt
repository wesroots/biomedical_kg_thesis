SECTION 4.7: CONTEMPORARY KNOWLEDGE GRAPH CONSTRUCTION

SUBSECTION: Named Entity Normalisation

Purpose:
Describe how entity mentions extracted from the CBC were converted from surface-form strings into standardised biomedical concepts before ontology-based validation and graph construction.

This subsection should answer:
“How were the raw entity mentions produced by the final extraction pipeline mapped to canonical biomedical concepts and identifiers suitable for use as KG nodes?”

Important:
Describe the NEN procedure that was actually implemented. Do not introduce or justify an alternative procedure here. The notes below are intended as a structural guide for writing up the implemented process.

Opening paragraph:

Briefly explain where NEN occurs in the implemented pipeline.
State that NEN was applied to entities extracted from the CBC by the frozen final EPI.
Explain that the extraction stage initially represents entities using their textual mentions and assigned entity types.
State that NEN converts these extracted mentions into standardised biomedical concepts/identifiers.
Explain the immediate purpose for KG construction: different surface forms referring to the same underlying biomedical concept should resolve to a common node rather than producing duplicate nodes.
Refer back to the Literature Review discussion of NEN rather than re-explaining the general theory or importance of entity normalisation.

Input to NEN:

Describe exactly what information from the extraction output was passed into the NEN process.
State which fields were used, such as entity mention, extracted entity type and PMID/document identifier, according to the actual implementation.
Explain whether normalisation operated on every extracted entity occurrence or on unique entity/type combinations.
If repeated mentions were normalised once and subsequently reused/cached, state this.
Explain how the relationship between the original extracted mention and its normalised representation was retained.
Make clear that relations were not independently normalised as textual objects; instead, their source and target entities could subsequently be resolved through the normalised entity records.

Terminology resource:

Identify UMLS and the specific UMLS component/resource used.
State how UMLS was accessed in the implementation.
State which UMLS release/version was used if this was fixed or recorded.
Explain what information was retrieved from UMLS that was relevant to normalisation, such as candidate concepts, CUIs, preferred names and alternative terms/synonyms, according to the actual implementation.
Be terminologically precise: do not describe the UMLS Metathesaurus as a single ontology.
Briefly justify UMLS as the normalisation resource in terms of its integration of biomedical terminology and concept identifiers.
Avoid repeating the broader discussion of biomedical ontologies/vocabularies from the Literature Review.

Candidate generation:

Describe exactly how candidate UMLS concepts were obtained for each extracted entity.
State the query/search procedure actually used.
State how many candidates were retained, if a fixed number was used.
State whether any filtering occurred before candidate ranking.
If extracted BioRED entity type was used during candidate retrieval/filtering, explain exactly how.
If it was not used at this stage, do not imply that it was; semantic-type checking may instead belong to the following ontology-validation subsection.
Explain what happened where UMLS returned no suitable candidates.

Candidate comparison/ranking:

Describe the implemented method used to determine which candidate concept best represented the extracted mention.
Identify the embedding model actually used.
State what text was embedded on the extracted-entity side.
State what candidate representations were embedded, such as preferred names and/or synonyms, according to the actual implementation.
Explain how cosine similarity was used to compare these representations.
If multiple synonyms belonged to a single candidate CUI, explain exactly how their similarity scores were combined or selected.
State how the final candidate CUI was selected from the candidate set.
Include the cosine similarity equation only if useful and not unnecessarily repetitive with Section 4.6. If the same equation has already been formally defined there, cross-reference it instead.

Acceptance threshold:

State whether a minimum similarity threshold was required before assigning a CUI.
Give the threshold actually used.
Explain how the threshold was selected or calibrated.
Clearly distinguish the NEN threshold from the cosine threshold used for extraction evaluation if they are different.
Explain what happened when the highest-scoring candidate failed to meet the threshold.
Avoid forcing every extracted entity onto a UMLS concept if the implementation allows an unresolved outcome.

Normalisation output:
Clearly define what the NEN stage produced.

For example, depending on the actual implementation, the resulting record may contain:

original extracted mention;
extracted entity type;
assigned CUI;
preferred/canonical UMLS name;
selected candidate/synonym;
similarity score;
PMID/provenance;
normalisation status.

A small table showing the output schema would work well here.

An illustrative example can also be useful:

Raw extracted mention
-> candidate comparison
-> selected canonical concept
-> CUI

Use one real example from the CBC if available rather than inventing one.

Handling unresolved entities:

State how entities for which no acceptable normalisation was identified were represented.
Explain whether they were retained as unresolved entities, excluded from subsequent KG construction, manually inspected, or handled in another way.
State what happened to relations containing an unresolved source or target entity, if this decision was made during NEN.
If relation handling actually occurs during graph construction rather than NEN, defer it to Section 4.7.3 instead.

Connection to relations and KG construction:

Do not describe the actual NetworkX construction here. Save node creation, edge creation, duplicate consolidation, provenance attributes and GraphML export for Graph Construction.

Relationship with ontology-based validation:
Keep the boundary between this subsection and the next one very clear.

Named Entity Normalisation asks:
“What standard biomedical concept does this extracted mention correspond to?”

Ontology-Based Validation asks:
“Is the resulting normalised concept semantically compatible with the extraction/schema?”

Therefore, this subsection should finish once a candidate concept/CUI has been assigned or the entity has been marked unresolved.

Do not pre-emptively explain the complete semantic-type validation procedure here unless semantic information was directly required as part of the implemented NEN algorithm. If it was, describe only its role in normalisation and leave the broader validation logic for the following subsection.

Expected length:
Approximately 600–900 words should be sufficient. The implementation details matter here, but there is no need to turn it into another literature review. The strongest version of this subsection will read primarily as a reproducible description of exactly what the code did.
