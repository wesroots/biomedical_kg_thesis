4.5.1 Extraction Pipeline Iterations

Purpose:
Document the sequence of methodological changes made during development.

This is the best place for your EPI configuration table.

Recommended table:

EPI | Prompt version | Evaluation version | Main change / purpose

For example:

epi_001 | v1 | v1 | Initial baseline
epi_002 | v2 | v1 | Added BioRED schema guidance
epi_003 | v3 | v2 | Added few-shot prompting
...
epi_009 | vX | vY | Final refinement

Use your actual configuration history rather than these example descriptions.

The “notes” column should be short and methodological. It should answer:
“What changed relative to the previous relevant EPI?”

Avoid putting performance results in the notes column unless a result directly motivated the next iteration.

For example, better:
“Added explicit grounding instructions to discourage unsupported relations.”

Rather than:
“Relation F1 dropped to 0.48.”

The latter belongs in the development discussion/results.

Explain that not every new EPI necessarily changed both prompt and evaluation logic. Some iterations may hold extraction outputs constant while changing only the evaluation approach. This is particularly important because Section 4.4.3 already explains that stored outputs were reused where the prompt/extraction configuration itself had not changed.

A short paragraph after the table can identify the broad development phases, for example:

baseline extraction;
BioRED schema alignment;
few-shot prompting;
relaxed evaluation;
cosine-based matching;
relation-specific prompt refinement;
grounding / unsupported-relation refinement.

This will make the sequence easier to understand than narrating nine EPIs one by one in full prose.

Evaluation logic: strict -> relaxed -> cosine

Yes, this absolutely belongs in 4.5.1, because the evaluation policy itself changed during iterative development.

However, distinguish between:

Section 4.5: why and when the evaluation logic changed during development;
Section 4.7: exact formal definitions and implementation of strict, relaxed, and cosine evaluation.

In 4.5, explain the development story.

Something like:

Initial EPIs were assessed using strict matching, requiring exact agreement between predicted and ground-truth entity representations. Inspection of resulting errors showed that some predictions represented the correct biomedical concept but differed in span boundaries or synonymous wording, meaning strict matching could classify semantically correct predictions as errors.

This motivated introduction of relaxed matching.

Then explain why relaxed matching was still insufficient:

rule-based relaxation can capture boundary overlap or predefined equivalence;
it cannot reliably identify semantically equivalent expressions with substantially different surface forms.

This then motivated cosine similarity matching using your embedding model and threshold.

The progression is therefore:

strict matching
-> identify boundary/synonym artefacts
-> relaxed matching
-> remaining semantic-equivalence problem
-> cosine similarity matching

That is a strong methodological development narrative because the evaluation changes are not arbitrary; they arose from observed limitations of the previous evaluation method.

Do not fully define formulas/threshold calculation here if 4.7 will do that.

Error sampling

I would include it, but only briefly.

The attached error distributions are useful because they demonstrate that your changes were driven by actual error inspection rather than only watching aggregate F1.

You do not need to include all three error-distribution figures in the main methodology.

Instead explain the procedure:

At selected development points, a sample of FP and FN relation errors was manually inspected.
Errors were assigned to predefined categories.
Example FP categories included:
unsupported relation;
wrong relation type;
entity boundary/synonym mismatch;
duplicate/coreference;
evaluation artefact.
FN categories included:
missing relation;
evaluation artefact.
These distributions were used diagnostically to identify whether poor measured performance reflected extraction failure, evaluation mismatch, or prompt behaviour.

The figures you attached show why this was useful:

unsupported relations remain a major FP category;
boundary/synonym mismatches are prominent in earlier/mid-stage sampling;
a substantial number of apparent FNs were evaluation artefacts;
missing relations remain the dominant genuine FN category.

That directly supports two major refinements:

improving grounding / reducing unsupported relation extraction;
improving evaluation from strict/relaxed matching toward semantic cosine matching.

If space is tight, I would not put all three figures in the main report. Instead:

describe the sampling method in 4.5.1;
perhaps include one representative error-distribution figure if it materially explains an important refinement;
place the remaining error-analysis plots in an appendix, or use them later in Results/Discussion.

The methodology needs to explain that error sampling occurred. It does not need to visually document every sample.

4.5.2 Development and Model Selection

Purpose:
Explain how frozen candidate EPIs were compared and how the final EPI was selected.

This is exactly where your two performance figures belong.

First figure:
The line chart showing precision, recall, and F1 across all EPIs for entities and relations.

Use it to show the overall development trajectory.

The important narrative from the chart is:

very large improvement from the baseline to the early refined configurations;
entity performance becomes comparatively strong and then broadly plateaus;
relation performance remains substantially lower than entity performance;
later EPIs produce smaller, incremental changes rather than the major gains seen early in development.

Do not overanalyse every point here. The figure is mainly there to show development progression.

The vertical lines marking important methodological changes are useful if they correspond to specific transitions such as:

introduction of few-shot prompting;
change to cosine evaluation;
important prompt revisions.

Explain those markers in the figure caption or surrounding text.

Second figure:
The bar chart comparing the top candidate EPIs.

This fits particularly well in 4.5.2 because it narrows the comparison to the configurations considered for final selection.

Your chart compares epi_005, epi_006, and epi_007 using relation precision, recall, and F1.

That is sensible because relation extraction appears to be the limiting component of the system, whereas entity extraction is already comparatively strong.

You should explicitly justify why relation performance played a major role in selection.

For example:

“Because entity-level performance had largely plateaued across the leading configurations, final selection placed greater emphasis on relation-level F1, while ensuring that entity performance remained stable.”

That is a defensible selection principle.

Do not simply say:
“EPI X had the highest score so it was selected.”

Explain the selection criterion:

primary metric;
whether entity performance was also considered;
whether precision/recall balance mattered;
whether error analysis influenced the decision.

If two EPIs are extremely close, acknowledge that rather than pretending there is a huge difference.

Also distinguish:

training-set development performance;
development-set candidate comparison.

The final selection must be based on the held-out BioRED development split according to the design you described earlier.

If the attached line chart is based on training-set development performance, label it clearly as such.

Then the top-candidate comparison should ideally show the development-set comparison if that is the actual basis of final selection.

This distinction is important.
