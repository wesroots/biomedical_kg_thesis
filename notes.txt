4.6.2 Relation Evaluation

Purpose:
Define exactly how predicted relations were compared against BioRED/CBC ground-truth relations.

Begin by defining the relation representation:

Explain that relation correctness therefore depends on both the relation label and its entity arguments.

Cover:

Relations were compared only within the same PMID/document.
Source and target entities were matched using the entity-matching procedure defined in Section 4.6.1.
Avoid repeating the complete strict/relaxed/cosine procedure; cross-reference 4.6.1 instead.
State that the predicted relation type must correspond to the ground-truth relation type.
Therefore, correctly identifying the two entities but assigning the wrong relation class does not constitute a correct relation prediction.

Relation order invariance:
This requires explicit explanation because it forms part of your final evaluation configuration.

Cover:

State which relation types were treated as symmetric/order-invariant.
Explain that, for those relations, reversing source and target did not cause an otherwise correct prediction to be marked incorrect.
Give one simple example if useful:
(A, Association, B) is equivalent to (B, Association, A)
If only selected relation classes are order-invariant, list them.
State that directional relation classes retained source-target ordering.
Do not imply that every BioRED relation is symmetric unless that is genuinely what your final implementation does.

Define relation TP/FP/FN:

TP: a predicted relation for which both entity arguments and the relation type match an unmatched ground-truth relation.
FP: a predicted relation with no corresponding ground-truth relation.
FN: a ground-truth relation for which no corresponding prediction was identified.
Explain one-to-one matching if implemented so the same ground-truth relation cannot satisfy multiple predictions.

Then state that relation precision, recall and F1 were calculated independently of entity-level metrics.

If your relation evaluation requires both endpoints to have been extracted correctly before a relation can match, make this explicit. This helps explain why relation performance can be lower than entity performance.
